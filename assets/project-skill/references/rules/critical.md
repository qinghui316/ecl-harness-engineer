# Critical Harness Rules

> Generated from `red_lines.yaml`. Do not edit this file directly.

## HR-01: Read Applicable Current State

Read critical rules and relevant project knowledge for every task. Structured work and every multi-Lane repository mutation read the current workflow and run coordination Registry preflight after recording initial scope; pure explanation, source research, and single-Lane Small Changes do not require preflight.

**On violation:** Stop and load the applicable knowledge, workflow, and shared state before continuing.

## HR-02: Structured Work Requires A Change

Cross-file, contract, architecture, permission, data, release, or multi-step work requires one Change and approved plan before implementation.

**On violation:** Return to intake or plan and obtain the project-native approval.

## HR-03: Record High-Impact Contracts

API, schema, event, config, permission, and module-boundary changes must record an evidence-backed contract in the coordination Registry.

**On violation:** Stop implementation, record the contract, and rerun preflight.

## HR-04: Preserve Project Integrity

Preserve unrelated user changes and never weaken or bypass existing project verification to make Harness work pass.

**On violation:** Stop, restore the intended scope without reverting user work, and report the affected gate.

## HR-05: User Controls Canonical Landing

Integration starts on an explicit user request and requires integration approval (I2) after independent review of the exact candidate commit before landing business code on the canonical branch.

**On violation:** Keep the Integration candidate pending and request independent review of the current candidate commit plus integration approval.

## HR-09: Validate Periodic Harness Review

Periodic Harness review requires E1 approval, one exclusive Evolution lease, a proposal, independent score at least 80, no blocking issue, and required validation.

**On violation:** Record rejected or noop and do not modify current Harness content.

## HR-11: Protect Stable Project Knowledge

Workers and ordinary Integration record evidence but do not rewrite shared L1/L2/L3 or global rules. Initialization, migration, and accepted Evolution may update stable project Harness content.

**On violation:** Move provisional facts to Change or coordination Registry evidence and restore the stable shared content.

## HR-15: Integrate Only Selected Commit Ranges

Apply each selected linear base_commit..completion_commit range; never merge a long-lived Lane tip as a whole.

**On violation:** Abort the candidate and rebuild it from the exact selected ranges.

## HR-17: Ground Semantic Bridges

L3 mappings require source code, manifest/configuration, tests, an integrated contract, or explicit user evidence; repository prose and search inference only locate candidates.

**On violation:** Remove the unsupported mapping or mark it unresolved.

## HR-19: Use One Exclusive Write Lock

Integration finalization and application of an accepted Evolution candidate must not overlap; acquire the project Harness exclusive write lock before changing stable content.

**On violation:** Stop and wait for or repair the process holding the existing lock.

## HR-21: Keep Knowledge Inspection Read Only

Knowledge scan and check only report source changes. Ordinary current, target, decision, and guide documents update directly in a Structured Change; change reindex or close maintains the catalog and source fingerprints. Full migration is reserved for current facts generated by full project analysis, Runtime/schema changes, or a full project knowledge refresh, and E1 retains independent review.

**On violation:** Stop the inspection and use the direct Change, full migration, or E1 path that matches the actual scope.

## HR-22: Use Source Precedence For Current Facts

When integration-base events or source changes affect the current scope, coordination Registry contracts and events, shared current Change evidence, and repository code/manifests/configuration/tests/interfaces take precedence over periodic L1/L2/L3; stop and replan with refresh-needed.

**On violation:** Discard the stale Wiki assumption, reload higher-priority current evidence, and revise the Change plan before continuing.

## HR-24: Bootstrap Business Code Through A Change

Create greenfield source, project commands, documentation, Make or CI only after purpose, stack, application type, and acceptance are confirmed in an approved Structured Change.

**On violation:** Stop business-project generation and return to bootstrap spec and plan review.

## HR-25: Detach Shared Harness Links Before Worktree Removal

Before removing a secondary worktree, verify that its Codex and Claude Skill links target the marked physical project Harness, then detach those link nodes without following their target.

**On violation:** Stop worktree removal, preserve the worktree and physical project Harness, and report the unverifiable or conflicting path.
