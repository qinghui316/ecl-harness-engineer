# Periodic Harness Evolution Review

## Inputs

- Fixed set of five Change IDs under review, compact coordination Registry summaries, selected
  Change/review evidence, and Integration signals.
- The generated knowledge catalog, affected current/target/decision/guide documents and their
  direct semantic neighbors, plus workflows, rules, templates, checks, relevant source-change findings,
  and canonical evidence only when the proposal affects project semantics.
- `references/analysis-contract.md`, which defines focused delta and full-refresh bundle boundaries.

## Agent Judgment

Classify accumulated experience as Promote, Retain, Merge, Retire, or Archive-only. Distinguish
current facts generated by full project analysis from agent-maintained project documents and
Harness process rules. Default to focused Evolution for agent-maintained L1/L2/L3. Require a full
refresh only when purpose, generated module/reference maps, architecture, commands, environment, or
related current-fact sources change.
Do not promote unintegrated implementation facts or generic
article advice without project evidence.
Before creating knowledge, search catalog entries by module, knowledge owner, kind, and task terms.
Prefer Merge or Replace; a proposal that chooses Create explains why existing documents with that
knowledge owner are insufficient.
Expand beyond affected documents only when evidence reveals wider overlap. A whole-catalog
retention review expands review scope but does not run the renderer. A full-refresh Evolution uses
the complete analysis bundle and renderer; a semantic audit remains read-only.

## Deterministic Commands

- Ask for periodic Harness review approval (E1), then run
  `evolve check --e1-confirmed --claim-owner <id>` to acquire the exclusive write lock followed by
  the Evolution lease. Both remain held through review and terminal result.
- For focused work, create `creation-delta.json` with `mode: evolution-focused` and only the named
  artifacts. For full refresh, run the draft extractor and complete the four control files plus any
  artifact payloads declared by `creation-delta.json`.
- Run `evolve stage --proposal-id <id> --owner <id> --analysis-bundle <bundle>` after the proposal
  and selected bundle exist. Stage validates the bundle; a separate project audit is not required.
- Run the affected Harness checks and necessary project validation. Run a full project test only
  when the changed knowledge/component owner or project contract requires it.
- After stage returns the candidate content digest, immediately request an independent reviewer.
  The author cannot perform the independent review.
- Persist the result using `assets/templates/evolution-judge.json`, bound to the candidate
  digest and a reviewer distinct from the process holding the Evolution lease.
- Run `evolve mark-complete --judge-report <path>` exactly once for keep/rejected. If no reviewer is
  available, use `--status noop --judge-unavailable`.

## Actions

1. Record the fixed set of five Change IDs; queue later Changes for the next review.
2. Select focused delta by default for agent-maintained documents and behavior; select a full
   refresh bundle only for current project facts generated by full project analysis.
3. Propose only evidence-backed knowledge, workflow, rule, template, check, and documentation-retention changes.
4. Remove duplicate current facts, retire stale guidance, and retain detailed history in archive.
5. Stage and validate the complete project Harness candidate, preserve
   `references/audit-rubric.json`, then recompute its content digest before a crash-recoverable
   whole-root transaction that preserves current mutable state.
6. Apply automatically only after score >= 80, no blocking issue, and all required validation passes.

## Outputs

- Proposal, evidence classification, focused delta or full bundle, independent review result, validation report,
  terminal results.tsv row, and either one accepted project Harness update or no modification.

## Exit

Evaluated IDs are durable, pending is closed, the exclusive Evolution lease and write lock are
released, and the terminal result is keep/rejected/noop. Status `keep` means accepted and applied;
status `noop` means review completed with no change applied. A kept run may update L1/L2/L3 and
Harness behavior without E2.

On transaction failure, current content and persisted Evolution state are restored while the
Evolution lease, exclusive-write-lock record, and staged candidate remain available for diagnosis
and retry.

## Stop And Escalate

Stop on missing E1, exclusive-write-lock collision, unsupported project fact, score below 80,
blocking issue, failed
validation, or unavailable independent review. Record rejected/noop rather than partially applying.

## Rules

Apply HR-01, HR-04, HR-06 through HR-13, and HR-16 through HR-21 plus
`references/rules/by-stage/evolve.md`.
